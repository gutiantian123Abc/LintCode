### Q1.1 Walk through A/B test concepts: alpha, beta, power, and how they relate to sample size. 【IGotAnOffer 收录】

**Answer.**

"Alpha is the Type I error rate — the probability of declaring a difference when none exists, i.e. P(reject H0 | H0 true). Convention is 0.05. Beta is the Type II error rate — the probability of missing a real effect, P(fail to reject | true effect exists). Power = 1 − beta, conventionally 0.8, is the probability of detecting an effect of a given size if it's really there.

These four quantities — alpha, power, the minimum detectable effect (MDE, δ), and the outcome variance σ² — jointly determine the required sample size. For a two-arm test on means:

    n per arm ≈ 2 · (z_{1−α/2} + z_{1−β})² · σ² / δ²

With α = 0.05 and power = 0.8, (1.96 + 0.84)² ≈ 7.85, so a handy rule of thumb is **n ≈ 16σ²/δ² per arm**. For a conversion metric, σ² ≈ p(1−p).

The relationships to call out:
- Stricter alpha (0.01 vs 0.05) → larger n.
- Higher power (0.9 vs 0.8) → larger n.
- **Halving the MDE quadruples n** — sample size scales with 1/δ². This is why detecting a 0.5% lift is 4× more expensive than a 1% lift.
- Lower variance → smaller n, which is why variance reduction (CUPED, stratification) directly buys you faster experiments.

In practice I fix alpha and power by convention, estimate σ from historical data, and set the MDE from business materiality — 'what's the smallest lift that would still justify shipping?' Then n gives me the duration given traffic; I round the duration up to full weeks to cover weekly seasonality."

**加分点**: "One caveat — this is the fixed-horizon calculation. If we're going to peek at results repeatedly, we should either commit to not deciding early, or use a sequential design (e.g., mSPRT / group-sequential bounds), otherwise the realized alpha is much higher than 0.05."

### Q1.2 For sample size n, the margin of error is 3. How many more samples do we need to make the margin of error 0.3? 【IGotAnOffer 收录】

**Answer.**

"Margin of error is MOE = z·σ/√n, so MOE ∝ 1/√n. To shrink MOE by a factor of 10 (3 → 0.3), n must grow by a factor of 10² = 100. So we need 100n total, i.e. **99n additional samples**.

The general takeaway: precision is expensive — each extra digit of precision costs 100× the data. That's exactly why in experimentation we care so much about variance reduction and about choosing an MDE we actually need, rather than 'as precise as possible'."

---

### Q1.3 What is a confidence interval and how do you interpret one? 【DataInterview 收录】

**Answer.**

"A 95% confidence interval is generated by a procedure that, over repeated sampling, produces intervals containing the true parameter 95% of the time. The subtlety: for any one computed interval, the parameter is fixed and the interval is random — so the strictly correct statement is about the *procedure's* long-run coverage, not '95% probability the true value is inside this interval' (that's the Bayesian credible-interval interpretation).

How I actually use it in experiments:
- Report the effect estimate **with** its CI, not just a p-value — the CI communicates both statistical significance (does it exclude 0?) and practical significance (are both ends of the interval big enough to matter?).
- Duality with testing: a 95% CI excluding 0 ⟺ two-sided p < 0.05.
- A CI that includes 0 but spans, say, [−0.1%, +3%] doesn't mean 'no effect' — it means we're underpowered; the decision-relevant reading is 'effect could plausibly be as large as 3%'.
- For relative lift (B−A)/A, the CI needs the delta method or bootstrap since it's a ratio of random quantities."

**加分点**: "Two practical failure modes: repeated peeking destroys the nominal coverage, and CIs for heavily skewed metrics (e.g., revenue) computed with normal approximations can be badly mis-calibrated at moderate n — I'd bootstrap those."

### Q1.4 When would you use a t-test versus a z-test? 【IGotAnOffer 收录】

**Answer.**

"A z-test assumes the standard error is known (or n is large enough that the estimated SE is essentially exact); a t-test accounts for the extra uncertainty of *estimating* the variance from the sample, using the t distribution with its heavier tails and n-dependent degrees of freedom.

Rules of thumb:
- Small samples, unknown variance, roughly normal outcome → t-test.
- Large samples → t and z converge; the distinction is immaterial in web-scale experiments where n is in the thousands or millions.
- Proportions (conversion rates) → two-proportion z-test / chi-square, since the variance is determined by p itself.
- My practical default for continuous metrics is **Welch's t-test** (unequal-variance t), because it costs nothing and is robust to variance differences between arms — the classic Student's t assumption of equal variances rarely holds after a treatment that changes behavior."

---

### Q1.5 Under what conditions would you use a t-test vs a proportion test vs bootstrap vs a non-parametric test?（电面 Python 环节延伸考点【实锤】）

**Answer.**

"I choose by (1) the metric type, (2) its distribution, and (3) what estimand I actually need:

- **Binary outcome (converted / not)** → two-proportion z-test or chi-square. A t-test on the 0/1 values is asymptotically equivalent, but I'd present it as a proportion test.
- **Continuous, well-behaved, decent n** → Welch's t-test. The CLT makes it robust to moderate non-normality once each arm has a few hundred observations.
- **Heavy-tailed / zero-inflated metrics (revenue, tokens used, tickets filed)** → the t-test is still *valid* at large n but can be low-powered and the normal CI can be poor. Options: (a) **bootstrap** the difference in means — keeps the estimand I care about (the mean, which maps to money) while getting honest CIs; (b) winsorize/cap outliers — but that changes the estimand, so state it; (c) log-transform — again changes the estimand to a ratio of geometric means.
- **Non-parametric (Mann–Whitney U)** when I only need 'does the distribution shift' and can't trust moments at all. Caveat I always mention: MWU tests stochastic dominance, **not** the difference in means — it can disagree with the revenue impact direction, so I don't use it for shipping decisions about money metrics.
- **Randomization unit ≠ analysis unit** (e.g., randomized by user, metric is per-session CTR) → the naive test is anti-conservative; use the **delta method** or a **clustered bootstrap resampling users, not sessions**.
- **Tiny samples** → permutation/exact tests (Fisher)."

### Q1.6 You run a 14-day A/B test on a ranking change; the daily metric has strong weekend seasonality and daily values are autocorrelated. How do you analyze it? 【DataInterview 收录题型】

**Answer.**

"The trap in this question is analyzing at the **day** level. Fourteen daily aggregates are (a) only n = 14 points and (b) autocorrelated, so a t-test across days is invalid and hopelessly underpowered.

The right approach: the randomization unit is the user, so **analyze at the user level**. Aggregate each user's outcome over the full window, then compare arms. Randomization guarantees both arms experience the same weekends and the same seasonality, so seasonality is not a confounder — it just adds variance that user-level analysis handles naturally.

What I'd still do about the calendar:
- Run for **whole weeks** (14 days = exactly 2 weekly cycles) so weekday/weekend behavior is represented in proportion — never 10 or 12 days.
- Check treatment × day-of-week interaction as a *heterogeneity* read (does the effect differ on weekends?), not as the primary test.
- Watch for ramp effects: if traffic was ramped mid-test, restrict to the stable period or stratify by entry cohort.

If the design forces time-level analysis — e.g., a **switchback** where we alternate treatments over time blocks — then autocorrelation is a first-order issue and I'd use block-level randomization inference or autocorrelation-robust (Newey–West type) standard errors."

### Q1.7 Causal inference toolbox: when you can't run an A/B test, what do you use, and what are the assumptions? 【实锤：VO stats 轮明确考 causal inference】

**Answer.**（每个方法答三件事：假设 → 假设何时会破 → 怎么检验）

"First, when can't we randomize? Legal/fairness constraints (pricing, support SLAs by contract), spillovers that break SUTVA, company-wide launches with no holdout, or events that already happened. Then the toolbox:

**Difference-in-Differences (DiD).** Compare change over time in treated vs untreated groups; identifies the effect under the **parallel trends** assumption — absent treatment, both groups would have moved in parallel. Breaks when treatment timing correlates with group-specific shocks (e.g., we rolled out to countries *because* their metrics were deteriorating). Checks: plot pre-period trends, run placebo DiD on pre-period, event-study specification. With staggered rollout across many units, naive two-way fixed effects can be biased — use modern estimators (Callaway–Sant'Anna style) or at least be explicit about cohorts.

**Regression Discontinuity (RDD).** Units just above vs just below a threshold (e.g., accounts above $X ARR get dedicated support). Assumption: potential outcomes are **continuous at the cutoff** and units can't precisely manipulate their score. Checks: McCrary density test for bunching at the cutoff, covariate smoothness at the cutoff, bandwidth sensitivity. Limitation: identifies a **local** effect at the threshold, not for everyone.

**Instrumental Variables (IV).** Need an instrument that moves treatment (relevance — first-stage F > 10) but affects the outcome only through treatment (**exclusion restriction**, untestable — must be argued). Classic use: randomized *encouragement* when you can't force treatment. Estimates a LATE for compliers.

**Matching / propensity weighting.** Assumes **unconfoundedness** — all confounders observed — which is strong; plus overlap/common support. Checks: covariate balance after matching, sensitivity analysis to unobserved confounding. I treat this as 'better than raw comparison', never as gold standard.

**Synthetic control.** One (or few) treated units, long pre-period: build a weighted combo of control units matching the treated unit's pre-history. Inference via placebo permutations across control units.

**CUPED / regression adjustment.** Not an identification method — a **variance-reduction** technique for experiments: Y_adj = Y − θ(X_pre − mean(X_pre)), θ = cov(X,Y)/var(X); variance shrinks by the squared pre-post correlation ρ², often 30–50% for retention-type metrics, i.e. experiments finish ~2× faster."

### Q1.8 User Ops 场景迷你题（把 Q1.7 落到本组业务）【推测，方向对口】

**Q: "We rolled out AI-drafted support replies country by country over 3 months — no randomization. How do you estimate the impact on resolution time?"**

**A.** "Staggered rollout → event-study DiD: for each country, align time relative to its launch date, compare to not-yet-treated countries, verify flat pre-trends, use a staggered-robust estimator. Guard against the killer confound: rollout order was probably chosen deliberately (biggest/easiest queues first), so I'd also show robustness excluding the first cohort and controlling for country-specific ticket-mix shifts."

**Q: "Enterprise accounts above a spend threshold get a dedicated support channel. Does dedicated support reduce churn?"**

**A.** "RDD at the spend cutoff: compare churn for accounts just above vs just below. Check for bunching (sales teams pushing accounts over the line to give them support — that's manipulation and would invalidate it), and report it as a local effect for mid-size accounts near the threshold, not for whale accounts."

**Q: "Does faster first-response time reduce churn? Response time isn't randomized — big customers get answered faster."**

**A.** "Direct regression is confounded by customer value. Options: (a) exploit quasi-random variation in queue load — e.g., a user filing a ticket just before vs after a staffing shift change or a demand spike shifts response time for reasons unrelated to the customer (an instrument); (b) within-customer designs comparing the same account's tickets across load conditions; (c) at minimum, matching on account attributes + sensitivity analysis. And I'd propose the real fix: run a bounded experiment on *non-contractual* users where we deliberately vary priority within an acceptable band."

### Q2.1 An A/B test shows a 0.2% drop in CTR but an increase in session length. How would you interpret these results? 【IGotAnOffer 收录】

**Answer.**

"Before interpreting, three checks: (1) is the CTR drop statistically significant, and is 0.2% absolute or relative? (2) SRM — is the split ratio as designed? (3) is CTR's *denominator* stable — if the feature changed how many impressions users see, CTR can move mechanically with no behavior change.

Then I'd reason about mechanisms, because these two metrics moving in opposite directions has at least two very different stories:

- **Good story**: users are getting value without needing to click — e.g., the answer is surfaced directly (very plausible in an AI product), so fewer clicks but longer, more engaged sessions.
- **Bad story**: users can't find what they want — they click less because results look worse, and sessions are longer because they're *struggling*, not engaged. Session length is a notoriously ambiguous metric: it rises both with delight and with friction.

To disambiguate, I go to metrics closer to user success: task completion / successful-session rate, query reformulation rate, bounce-after-click, downstream conversion or retention, and complaint/support-contact rate. Segment by user tenure and platform — if the CTR drop concentrates in power users, that's more worrying.

Decision framing: neither CTR nor session length should be the decision metric by itself. I'd map both to the pre-agreed primary metric (e.g., successful sessions or weekly retention). If success metrics are flat-to-positive and CTR is down only because users need fewer clicks, I lean ship; if reformulations and support contacts are up, that's a struggle signal — don't ship, iterate. If the data can't distinguish the two stories, extend the test and add the instrumentation, and I'd say exactly that — showing you *won't* force a launch decision from ambiguous data is part of what's being graded."

---

### Q2.2 After a launch, some metrics went up and others went down. Do you ship it? 【Exponent 收录，Meta 经典】

**Answer.**

"My framework, in order:

1. **Pre-registered hierarchy.** Before the test we should have agreed: one primary decision metric, a few secondaries, and guardrails with veto power. If the primary is up and no guardrail is breached, default is ship — mixed secondaries are expected noise, since with 20 metrics at α=0.05 one 'significant' decline appears by chance alone.
2. **Is the 'down' real?** Check significance, multiple-testing context, and consistency across segments/time. A −0.5% with CI [−1.8%, +0.8%] is not evidence of harm.
3. **Common currency.** Where possible, translate the ups and downs into one unit — incremental revenue, LTV, or cost. +2% conversion vs −1% margin per order has a computable net.
4. **Concentration of harm.** A small average decline that's concentrated in one segment (new users, one platform, accessibility-sensitive users) can be disqualifying even if the average is fine — check heterogeneity before averaging it away.
5. **Short vs long term.** Novelty effects and learning curves: check whether the negative metric is recovering over the test window; consider a long-term holdout.
6. **Decision options are not binary**: ship, don't ship, ship-to-segments, iterate on the losing surface, or extend for power. State the option and the reason.

Example: 'containment +15% (primary, significant), CSAT −2pts (guardrail, significant, concentrated in billing intents)' → I don't ship globally; I ship excluding billing intents, fix billing flows, re-test."

### Q2.3 You run 8 experiments simultaneously; one shows p = 0.03 on conversion but p = 0.20 on margin. What's real? 【DataInterview 收录】

**Answer.**

"Two separate issues here: multiplicity across experiments, and metric disagreement within one.

**Multiplicity.** With 8 independent tests at α = 0.05, the chance of at least one false positive is 1 − 0.95⁸ ≈ 34%. So 'one of eight experiments hit p = 0.03' is weak evidence by itself. Corrections: Bonferroni (0.05/8 = 0.00625 — this result fails), or better, Benjamini–Hochberg FDR if we accept a share of false discoveries. My practical stance: treat p = 0.03 in this context as a *promising lead*, then re-run it as a confirmatory experiment with a single pre-registered primary metric — replication is the cleanest multiplicity fix.
**Conversion vs margin.** p = 0.20 on margin does **not** mean 'no margin effect'. Margin is a revenue-type metric: heavy-tailed, high variance, much lower power than conversion at the same n. The right read is the point estimate and CI: if margin's CI comfortably contains the value implied by the conversion lift (e.g., conversion +2% should mechanically produce margin +~2% at stable basket size), the data are *consistent*, just underpowered on margin. If margin's point estimate is negative while conversion is up, investigate mix shift — the new converts may be lower-value (discount-driven signups), which changes the business read entirely.

Also worth checking with 8 concurrent experiments: overlapping populations and interaction effects — usually fine with orthogonal (independent hashed) assignment, but I'd verify the assignment design and run a quick interaction check between the big movers."

---

### Q2.4 You randomize by user_id, but users see different variants across devices. How do you detect and quantify the interference/contamination? 【DataInterview 收录】

**Answer.**

"This is identity fragmentation: one human = several user_ids/cookies (logged-out web, phone app, work laptop), so the same person can be exposed to both variants. Effects: (a) **dilution/attenuation** — treated people partially experience control and vice versa, biasing the estimate toward zero; (b) inconsistent UX can itself cause confusion effects.

**Detect & quantify:**
- Use post-hoc identity resolution (login linkage, device graph) to stitch ids belonging to the same person; compute the **contamination rate** κ = share of resolved identities whose ids fall in both arms, and the share of a treated person's activity actually spent under treatment (exposure purity).
- Compare effect estimates on the clean subpopulation (single-device, always-logged-in users) vs everyone: a materially larger effect among pure-exposure users is the signature of dilution. (Careful: that subgroup is self-selected, so treat it as a bound, not the truth.)
- Simple bias intuition: if a fraction κ of each arm effectively experiences a 50/50 blend, the measured effect ≈ true effect × (1 − κ), so a first-order correction is dividing by (1 − κ) — I'd present that as a sensitivity analysis, not a point fix.

**Prevent:** randomize on the most stable identity available (logged-in account id), bucket by account not cookie, restrict the experiment to logged-in surfaces, or accept ITT-on-cookie as the estimand and state that it lower-bounds the per-person effect."

### Q2.5 How do you design an A/B test when there are network effects? 【IGotAnOffer 收录】

**Answer.**

"Network effects violate SUTVA — my outcome depends on your treatment — so naive user-level randomization is biased (usually toward zero for positive spillovers, and it can even flip signs in marketplaces where arms compete for shared supply).

Designs, in order of common use:
- **Cluster randomization**: randomize communities that interact internally but not across — geos, companies/workspaces (natural for ChatGPT Enterprise), social-graph clusters. Analyze at cluster level or with cluster-robust SEs. Cost: fewer effective units → less power → need bigger effects or more clusters.
- **Switchback**: randomize time blocks (all traffic treated in block t, control in t+1), for marketplace/shared-resource settings; handle autocorrelation and carryover with washout periods.
- **Ego-cluster designs**: treat a focal user plus their whole neighborhood; measure on the ego.
- **Dosage/spillover designs**: randomize the *fraction* treated within clusters (0%, 50%, 100%) to measure the spillover directly rather than just avoiding it.

**User Ops specific**: support has a shared-capacity interference — if treatment deflects tickets, human agents' queues shrink, so control tickets get answered faster too, biasing against the treatment. For staffing/queue-level interventions I'd switchback by time window or randomize by site/queue; pure user-level randomization is fine only for interventions that don't touch shared capacity much (e.g., help-center content)."

### Q2.6 Experiment-design case 万能框架（本轮设计部分照此走）【多源印证】

**Answer skeleton (say this out loud, in this order):**

1. **Clarify** — business goal, the decision to be made (ship / iterate / kill), success definition, constraints (traffic, time, contractual SLAs).
2. **Hypothesis & mechanism** — what behavior changes, through what path.
3. **Design** — randomization unit (user / ticket / time-block / cluster; justify via interference), eligibility, triggering point (assign at exposure, not before), expected contamination.
4. **Metrics** — one primary (decision), secondaries (mechanism), **guardrails with veto** (CSAT, churn, safety, latency); exposure-based denominators.
5. **Power** — MDE from materiality, n and duration (whole weeks), variance reduction (CUPED).
6. **Run-time quality** — SRM alarm, logging of assignment + exposure, no peeking (or sequential plan), pre-registered segments.
7. **Analysis & decision rule** — stated before launch: 'ship if primary ≥ X with guardrails flat'; sensitivity analyses; heterogeneity; long-term holdout if effects may drift.
8. **What would change my mind** — say it explicitly; it's a listed evaluation point.

## Round 3 — HM Deep Dive（项目深挖）

**形式**【实锤】：deep dive 你自己的一个项目；有面经明确挂在这轮，死因是缺 high-level strategic thinking。这轮没有"题库"，给出英文陈述模板 + 高频 follow-up 及答法。

### Presentation template (10 min version)

1. **Context & stakes (1 min).** "The business problem was X; it mattered because $Y / Z% of users were affected. I owned the problem end-to-end." — 先讲钱和规模，不是先讲模型。
2. **Framing (2 min).** "The naive framing was A; I reframed it as B because…" — 展示你定义问题的能力，这是 senior 信号。
3. **Approach & key decisions (3 min).** 2–3 个关键技术决策，每个都讲 tradeoff："I chose DiD over matching because rollout timing gave me clean pre-trends, and matching couldn't handle the unobserved seasonal demand confounder."
4. **Obstacle (1 min).** 一个真实的坑 + 你怎么发现和修的（data leakage、SRM、logging bug…）。
5. **Impact (1 min).** 量化到决策和钱："The analysis reversed the planned rollout; we shipped to 3 segments instead of GA, saving ~$X while keeping Y% of the lift."
6. **Strategic layer (2 min) — 挂经指出的缺失项，必讲。** "Beyond this project: it became the team's standard playbook for Z; if I scaled it 10×, the bottleneck would be W; the next investment I proposed was V."

### 高频 follow-up 及答法

- **"Why this method and not something simpler?"** → Always show you *tried or considered* the simple thing first: "A pre/post comparison was the 2-hour version; it was confounded by seasonality, which I showed by X, hence DiD."
- **"How did you validate the result?"** → placebo tests, holdout replication, triangulation with an independent data source, sensitivity to assumptions.
- **"What did stakeholders disagree with, and what happened?"** → one concrete pushback + how data (or a scoped follow-up) resolved it. Never "everyone agreed."
- **"What would you do differently?"** → a real regret with a process fix, not "I'd have more data."
- **"How does this connect to company strategy?"** → practice one sentence linking the project to the org's top-line goal.

### Q4.1 Walk me through the lifecycle and cost of customer acquisition. 【IGotAnOffer + Glassdoor 双收录，唯一双源真题】

**Answer.**

"The lifecycle: **Awareness → Acquisition → Activation → Retention → Revenue → Referral** (the AARRR funnel). A user hears about the product, signs up (acquisition), reaches the first-value moment (activation — for ChatGPT, something like completing a first successful conversation within day 1), builds a habit (retention), converts to paid (revenue), and brings others (referral, which lowers the *next* user's acquisition cost).

**CAC** = fully-loaded acquisition spend / new customers acquired in the period. Distinctions that matter:
- **Blended vs paid CAC**: blended divides by all new users including organic; paid divides marketing spend by paid-attributed users only. Blended flatters you when organic is strong.
- **Average vs marginal CAC**: the next dollar of spend usually acquires a worse user than the average dollar — expansion decisions should use marginal CAC.
- **Attribution**: last-touch/first-touch are conventions, not causality; the honest tools are incrementality experiments (geo holdouts, PSA tests) and MMM at portfolio level.

CAC only means something next to value: **LTV** = margin per user per period × expected lifetime (discounted), estimated from cohort retention curves rather than a single churn number. Health heuristics: LTV:CAC ≥ 3, CAC payback < 12 months (payback = CAC / monthly gross margin per user).

**Tie to this role** (加分点): "For OpenAI specifically, acquisition is largely organic/word-of-mouth, so classic paid CAC is small — the acquisition cost that *does* exist looks like promotions, e.g. a free month of Plus. That's exactly the take-home scenario: the 'CAC' of a free-trial campaign is the subscription revenue forgone plus inference cost for trial users, and the return is incremental conversions × LTV — measured against the counterfactual of who would have subscribed anyway."

---

### Q4.2 How would you measure the success of a product? 【IGotAnOffer 收录】

**Answer.**

"Structure: mission → user value → business value, each with metrics, plus guardrails.

1. **Define the job-to-be-done** and the target user first — 'success' is meaningless until we say who it's for and what problem it solves.
2. **User value metrics**: adoption (reach of the feature among its intended audience), engagement depth (not raw DAU but *successful* use — task completion), and **retention** — the single strongest signal that value is real. I look at cohort retention curves: do they flatten above zero? Where does the flattening asymptote sit vs comparable products?
3. **Business value**: conversion to paid, ARPU, margin (for LLM products, inference cost per user matters — a feature can be engagement-positive and margin-negative), and efficiency metrics if it's an internal/ops product.
4. **Guardrails / counter-metrics**: quality, trust & safety incidents, support contact rate, latency, cannibalization of adjacent surfaces. Every north-star should have a named counter-metric so we notice when we're buying the metric with something we care about.
5. **Leading vs lagging**: pick 1–2 leading indicators (activation rate, week-1 habit) that predict the lagging outcomes (LTV, churn), validate the link empirically, and manage the team on the leading ones.

Then one **North Star** on top — see Q4.5 — with an input-metric tree so every team sees which lever they own."

### Q4.3 Activity in a product feature is down by 20%. What do you do? 【IGotAnOffer 收录】

**Answer.**

"I run a triage tree, fastest checks first — most 'metric crashed' incidents are data bugs, not user behavior.

1. **Is the data right?** Check the metric's pipeline: logging/SDK release same day? schema change? bot-filter change? Compare against an independent source measuring the same behavior (server logs vs client events). Check whether *other* metrics from the same pipeline dropped in lockstep — a clean signature of instrumentation breakage.
2. **Definition & denominator.** Did the metric definition or the eligible population change? A surge of new users can dilute a per-user rate without any absolute decline.
3. **Segment to localize.** Break by platform/app-version (a bad iOS release?), geo (one country = regulation/outage/holiday), user tenure (new vs core), and entry point. A 20% global drop that's actually −80% on Android pinpoints the cause; a uniform drop across all segments points to systemic causes (data, seasonality, external).
4. **Time alignment.** Sharp cliff on a date → find what shipped that date (release calendar, experiment reaching 100%, marketing stop). Gradual decline → seasonality (check YoY), competitor, novelty decay.
5. **Funnel decomposition.** activity = eligible users × visibility of entry point × click-through × completion. Find which stage broke — e.g., a redesign that moved the entry point below the fold shows up as a visibility drop with stable completion.
6. **Then act**: fix the root cause, backfill/annotate the metric if it was a data issue, and add an alert + ownership so the next 20% drop is caught in a day, not a month.

Throughout, I'd state priors out loud: 'in my experience the base rates are roughly: data/logging ≫ release/UX change > seasonality > external' — showing calibrated instincts is part of the answer."

### Q4.4 Delivery speed improved, but customer service contacts increased 12%. Diagnose. 【DataInterview DA 收录 — support 场景原题，User Ops 面出同款概率极高】

**Answer.**

"First, resist the framing that the speed improvement *caused* the contacts — establish the link before explaining it.

1. **Normalize the metric.** Contacts up 12% — is *volume* up (more orders → mechanically more contacts) or **contact rate per order** up? If orders grew 15%, contact rate actually fell. This single check often ends the investigation.
2. **Decompose by contact reason code.** Support contacts are a mixture; find which reasons drove the increase. If it's 'where is my order', that's odd given faster delivery — suspect notification/tracking confusion. If it's 'damaged item', faster handling may have increased damage. If the increase is in reasons unrelated to delivery (billing, returns policy), the timing is coincidental.
3. **Exploit rollout structure.** Delivery-speed improvements rarely launch everywhere at once — compare regions/warehouses that got the speed change vs not (DiD): did contact rate rise *differentially* where speed improved? If yes, causal link is credible; localize further by reason.
4. **Check the side effects of the mechanism.** How was speed achieved? New courier (different damage/mis-delivery profile), changed cutoff times (customer expectation mismatches), split shipments (multiple deliveries per order → more confusion, and possibly *more contacts per order* by construction).
5. **Quantify and recommend.** E.g., '+12% contacts = +9pts from split-shipment confusion, +3pts from volume; fix = merge shipment notifications + proactive tracking message; expected to recover 7pts; monitor weekly by reason code.'

**OpenAI translation** (加分点): same skeleton fires when 'we shipped a faster/better model and support contacts rose' — decompose by contact reason and check whether the model change shifted usage volume, user mix (an influx of new users always raises contact rate), or genuinely created new confusion."

### Q4.5 Define and choose a North Star metric for a product. 【DataInterview 收录】

**Answer.**

"Criteria for a good North Star: (1) it measures **value delivered to users**, not activity — sessions can rise while value falls; (2) it's a **leading indicator** of the long-term business outcome (retention/revenue), with the link empirically validated; (3) teams can **move** it and see movement at decision cadence; (4) it's **hard to game** — pair it with named guardrails anyway.

Canonical examples: Spotify — time listening; Airbnb — nights booked; a messaging app — DAU with ≥1 message sent to a friend. Bad North Stars: registered users (vanity, lagging nothing), raw time-on-site for a utility product (confuses friction with value).

Process: articulate the exchange of value → pick the metric closest to 'user got the job done' → build the **input tree** (North Star = reach × activation × frequency × depth …) so each team owns an input → validate against retention/revenue with cohort analysis → set counter-metrics.

**For a support org / User Ops** (likely follow-up here): my North Star candidate is **'% of user issues fully resolved within target time'** — it forces the tension between automation and quality into one number. Contact rate alone rewards making support hard to reach; deflection alone rewards walls; CSAT alone ignores the users who never got help. Guardrails: CSAT/DSAT, reopen rate, escalation availability, cost per resolution."

### Q4.6 We're reducing fees in 5 countries. Propose the success metric, a decomposition, and guardrails. 【DataInterview 收录】

**Answer.**

"**Success metric**: incremental **net contribution** = Δ(volume × take) − fee revenue given up on existing volume. A fee cut always loses money on the base; success means the elasticity response (more transactions, more sellers/users) outgrows the giveaway within a stated horizon (e.g., 12 months, discounted).

**Decomposition** (profit tree, say it as a tree):
Net contribution = transactions × average order value × take rate − costs, where transactions = active sellers × listings per seller × conversion; the fee cut should move seller acquisition/retention and price-competitiveness → conversion. Instrument each link so we can see *where* the response happens and how fast.

**Measurement design**: 5 countries were chosen, not randomized → treat as quasi-experiment: DiD against matched control countries (similar trends, seasonality, market maturity) or synthetic control per treated country; event-study plot to verify parallel pre-trends; account for cross-country spillovers (arbitrage, sellers shifting inventory across borders).

**Guardrails**: quality mix (fee cuts attract low-quality supply → track defect/refund/complaint rates), support contact rate, fraud rate, competitor response (price wars make the pre-period a bad counterfactual), margin floor, and cannibalization from neighboring non-treated countries.

**Decision rule stated upfront**: e.g., 'roll out further if incremental contribution turns positive within X months with quality guardrails flat; roll back if volume elasticity < E by month 3.'"

### Q4.7 A conversion dashboard by store for a VP: what's your default chart, and how do you avoid overreacting to small-sample stores? 【DataInterview DA 收录】

**Answer.**

"**Default view**: top — the aggregate conversion trend over time (weekly, with a YoY or target reference line), because the VP's first question is 'are we OK overall'. Below — a ranked bar chart of stores for the latest period, each bar with a **confidence interval**, and volume shown next to the rate (a rate without its denominator is uninterpretable). Time-series small multiples for the top/bottom movers, not a 200-line spaghetti chart.

**Against small-sample overreaction**:
- Show CIs and shade stores whose CI overlaps the network average — 'not distinguishable from average' should be visually boring.
- **Empirical-Bayes shrinkage**: display rates shrunk toward the network (or region) mean in proportion to sample size; a 5-visit store showing 80% conversion shrinks toward the mean, a 10,000-visit store barely moves. Label it as 'adjusted rate'.
- A **funnel plot** (rate vs volume with control limits) as the outlier-detection view: only stores outside the limits deserve a conversation.
- Aggregate small stores weekly/monthly instead of daily; set a minimum-n threshold below which the cell shows volume, not rate.
- Alerting on statistical control (SPC-style) rather than raw rank changes, so the VP's attention goes to real shifts — the deliverable is fewer, truer alarms."

## Case 1（旗舰，experiment 轮最可能）: "Our AI support agent currently handles Free-tier users. We want to expand it to Plus (paid) users. Design the experiment and make the launch decision."

**Full worked answer（照此完整讲一遍 ≈ 15 分钟）:**

**1. Clarify.** "What does the agent do today — full resolution with human fallback, or draft-only? For Plus users, what's the current human-support baseline (response time, CSAT)? Any contractual SLAs? And what's the decision: full rollout, or rollout-by-intent?" (Assume: agent fully handles chats with a 'talk to a human' escape hatch; decision is ship/no-ship/segment.)

**2. Hypothesis & mechanism.** "The agent resolves common issues instantly (vs hours for human queues), so resolution speed and cost improve; the risks are wrong answers on complex/billing issues and paying customers feeling fobbed off — quality and churn risk, asymmetric because Plus users carry revenue."

**3. Design.**
- **Randomization unit: user, not ticket.** The same user files multiple tickets; ticket-level randomization contaminates the experience (AI today, human tomorrow) and violates independence. Assign each Plus user contacting support to treatment (AI-first with human escalation) or control (status quo human queue), deterministic hash, assignment at first support contact (trigger point), logged with timestamps.
- **Eligibility & carve-outs**: exclude intents where mistakes are high-stakes from day one — billing disputes, account security, safety-adjacent content, legal/GDPR — those stay human in *both* arms (this is the responsible-deployment point; say it unprompted).
- **Stratify** by tenure (new vs long-time subscriber) and prior contact history; consider country/language as the agent's quality varies by language.
- **Interference check**: treated tickets deflected from the human queue shorten control users' wait times → biases *against* treatment on speed metrics. With small treatment share (e.g., 10% ramp) it's second-order; acknowledge it, and if measuring queue effects is essential, switchback by time window instead.

**4. Metrics.**
- **Primary**: resolution rate within 24h at acceptable quality — concretely, % of contacts fully resolved (user confirms or no reopen within 72h) — because it forces speed and quality into one number.
- **Secondary (mechanism)**: containment rate, time to resolution, escalation rate, cost per resolution, agent-turn count.
- **Guardrails (veto power)**: CSAT/DSAT on the contact, reopen rate, 7/30-day subscription churn of contacting users, complaint escalations to social/exec channels, and a **safety guardrail** — audited rate of materially wrong answers (from QA sampling), with a pre-agreed absolute ceiling.
- Exposure-based denominators: only users who actually contacted support.

**5. Power.** "Support contact rate for Plus might be ~[3–5]% of subscribers/month — the sample is *contacting users*, so traffic is limited; that pushes toward (a) a longer window (4+ weeks), (b) CUPED using pre-period contact/tenure covariates, (c) an MDE that's business-material — e.g., cost per resolution −20%, churn guardrail powered to detect +0.5pp."

**6. Run-time quality.** SRM alarm on arrival rates; monitor guardrails with alert thresholds for early stopping on harm (stopping for *harm* is always allowed; stopping early for *benefit* needs sequential correction); pre-register the segment cuts (intent × tenure × language).

**7. Decision rule (state before launch).** "Ship if primary ≥ control − ε with cost per resolution down ≥ X% and all guardrails flat (CSAT within −0.5pt, churn within +0.2pp). Ship-by-segment if harm concentrates in specific intents/languages. No-ship if churn or safety guardrail breaches, regardless of cost savings."

**8. Read-out（面试官常给一组混合结果让你拍板）.** Example: containment 62%, cost/resolution −35%, CSAT −1.8pt concentrated in billing-adjacent intents, churn flat. Answer: "Don't ship globally. The harm is legible and concentrated: route billing-adjacent intents straight to humans (they were supposed to be carved out — tighten the intent classifier), ship the rest, re-measure. I'd also invest in the handoff experience: most CSAT damage in AI-first support happens in the escalation moment — users repeating themselves to the human. Fix: pass full context on handoff and measure 'repeat-yourself' complaints."

**9. What would change my mind.** "If 'containment' is inflated by users *giving up* (silent failure), the whole read flips — so I'd validate containment against reopen-within-72h and a follow-up resolution survey on a sample. That's the metric I'd trust least by default."

## Case 2: "Support contacts jumped 30% this month. Diagnose."（DataInterview 有 12% 同款）

**Worked answer:**
"Triage tree: (1) **Real or artifact?** New contact channel launched (in-app button = lower friction → more contacts without more problems), dedup logic change, bot/spam wave. (2) **Normalize**: contacts per 1k active users — did usage grow 30%? A launch month with +40% new users *should* raise contacts; new users always contact more. Decompose: Δcontacts = Δusers × rate + Δrate × users (mix-shift decomposition, quantify each term). (3) **Localize**: cut by contact reason, product surface, plan tier, geo/language, tenure. A spike concentrated in 'can't log in' + one date = incident; spread across reasons + new users = growth mix. (4) **Align the timeline**: model releases, pricing/policy changes, outages, viral moments. (5) **Respond on two horizons**: short-term — staffing/queue triage, macros, status-page comms (cheap and immediate); long-term — if one friction driver dominates, that's a product fix with a quantified case: 'reason X = 9pts of the 30; fixing the flow saves ~$Y/quarter in support cost plus the churn effect.' (6) **Prevent**: reason-level anomaly alerts with owners, so next time it's caught in days."

## Case 3: "Forecast support ticket volume to plan staffing."（DataInterview 统计题原题场景 + JD 第一条职责）

**Worked answer:**
"**Framing first: the loss is asymmetric.** Under-staffing burns SLAs, CSAT, and agent burnout; over-staffing burns money — and the cost ratio is not 1:1. So the deliverable is not a point forecast: it's a **distributional forecast** (P50/P90) plus a staffing rule ('staff to P80 of forecast, flex with on-call/BPO for the tail').

**Structure of the series**: weekly seasonality (weekday>weekend), holidays, trend from user growth — and the dominant special ingredient at OpenAI: **launch spikes**. Product releases create step-changes and surges history can't predict from the series alone → the single highest-ROI feature is piping the **launch calendar** in as a regressor, with spike magnitude learned from past launches scaled by expected reach; add incident indicators for outage-driven bursts.

**Models, in escalating order**: seasonal-naive & moving-average baselines (always ship the baseline first — it sets the bar and often nearly matches fancy models on stable series); then a seasonal model with regressors (SARIMAX / Prophet-style with holiday + launch terms); then GBM on lagged features if there's rich metadata (per-queue, per-language forecasts). Hierarchy matters: forecast per queue × language (staffing is per skill group), reconcile to the total.

**Evaluation**: rolling-origin backtests; report **MAPE for accuracy and bias separately** — a symmetric-looking MAPE can hide systematic under-forecasting, and bias is what kills staffing; evaluate P90 coverage (did actual exceed P90 ~10% of the time?). Business metric of the forecast: SLA attainment and overtime cost, not MAPE for its own sake.

**Ops loop**: forecast weekly at 4–8 week horizon for hiring, daily at 1–2 week horizon for scheduling; monitor forecast-vs-actual with alerting; postmortem every big miss into the feature set (usually a missing launch/incident flag)."

## Case 4: "How do you evaluate the quality of an AI support agent?"（对应 model-eval take-home track【实锤】）

**Worked answer:**
"Two layers — offline and online — and the discipline is keeping them honestly connected.

**Offline**: build a **golden set** stratified by intent × language × difficulty × customer tier, refreshed as the product changes (stale evals are the #1 failure mode). Score with a human rubric: correctness (against known policy/answer), policy compliance, safety, tone, and actionability — with **inter-rater agreement (Cohen's κ)** measured before trusting labels. Scale it with **LLM-as-judge, but calibrated**: the judge is a model too, so validate judge-vs-human agreement per intent, track judge drift, and never let the judged model's own family grade it without a bias check. Report per-bucket, not one average — a 92% overall accuracy hiding 60% on billing intents is a shipping blocker, not a decimal point.

**Online**: containment rate, escalation-request rate, follow-up-question depth, reopen-within-72h, CSAT on AI-resolved contacts, and sampled human QA audits of live transcripts (the ground truth for 'materially wrong answer rate'). Crucially, **validate the proxy**: 'user stopped replying' ≠ resolved — some users give up. Cross-check silent closes against reopens and a lightweight resolution survey; if containment and reopen disagree, trust reopen.

**Statistical rigor**: eval sets are samples — put CIs on eval metrics (bootstrap), size the golden set to distinguish model versions at the deltas we care about (detecting a 2pt accuracy gap needs ~[hundreds] per bucket), correct for multiple comparisons across dozens of intent buckets.

**Connecting layers**: offline gates deployment (safety floor), online decides (experiment per Case 1). Offline wins that don't reproduce online usually mean the golden set has drifted from real traffic — measure distribution shift between eval set and live intents.

**Risks named unprompted**: Goodhart (optimizing containment → agent discourages escalation), eval-set leakage into training/prompts, and judge-model bias."

## Case 5: "We revamped the Help Center. How do you measure success?"

**Worked answer:**
"The trap is **deflection accounting**: 'user read the article and didn't file a ticket' conflates *resolved* with *gave up*. My measurement: define a session-level funnel — search/land → article read → (a) explicit feedback ('did this help?'), (b) ticket filed within the same session/24h, (c) return-with-same-issue within 7d. **Success = self-service resolution rate** := issue sessions ending with no ticket AND no recurrence AND (where present) positive feedback; guardrails: overall resolution rate (the issue got solved *somewhere*), CSAT of users who did file tickets afterward (did the detour make them angrier), time-to-resolution including the self-serve attempt. Causal read: content changes are site-wide, so randomize where possible (article-level A/B on search ranking / layout), otherwise geo or language-cohort DiD around the revamp. Also report the honest tradeoff: help-center friction can suppress tickets while suppressing satisfaction — falling contacts with rising 'gave up' signals is a failure that naive deflection metrics report as success."

## Case 6: "Design the support tiering strategy for enterprise customers."（JD 提到 enterprise support strategies）

**Worked answer:**
"Frame as cost-to-serve vs value-at-risk. (1) **Segment** accounts by ARR, usage criticality (API prod dependency vs exploratory), and support intensity; estimate cost-to-serve per account and churn-risk-weighted revenue. (2) **Design tiers**: SLA levels (response/resolution targets), channel access (dedicated Slack, TAM, AI-first vs human-first), priced or bundled by tier. (3) **Measure the causal value of premium support** — the hard part, since tiers aren't randomized: use the eligibility threshold (RDD at the ARR cutoff, per Q1.8), or grandfathering/rollout timing for DiD; outcome = renewal rate, expansion revenue, incident-time-to-recovery. (4) **Optimize**: if dedicated support's causal lift on renewal is concentrated in mid-market accounts with production API dependence, shift investment there and let AI-first handle low-criticality tiers — with the Case-1 quality guardrails. Deliverable: a tiering matrix with per-tier unit economics and a measurement plan, not just a org-chart proposal."

## D1. SQL 原题（你贴的面经"问题 2"，users/events 两表）

**Q1: Count users per country.**

```sql
SELECT country, COUNT(*) AS user_cnt
FROM users
GROUP BY country
ORDER BY user_cnt DESC;
```

**Q2: Daily active users (≥1 event, deduplicated).**

```sql
SELECT DATE(event_time) AS event_date,
       COUNT(DISTINCT user_id) AS dau
FROM events
GROUP BY 1
ORDER BY 1;
```

**Q3: Each user's first event time and type.**

```sql
SELECT user_id, event_time AS first_event_time, event_type AS first_event_type
FROM (
    SELECT user_id, event_time, event_type,
           ROW_NUMBER() OVER (
               PARTITION BY user_id
               ORDER BY event_time, event_id      -- tie-breaker: 同一时刻两条事件时保证确定性
           ) AS rn
    FROM events
) t
WHERE rn = 1;
```

说一句 tie-breaker（`event_id` 兜底排序）是加分点——面试官喜欢确定性。

**Q4: For each country, daily active users for the last 7 days (incl. today), ascending by date.**

```sql
-- 字面理解：最近 7 个自然日、每个国家每天的 DAU
SELECT u.country,
       DATE(e.event_time)            AS event_date,
       COUNT(DISTINCT e.user_id)     AS dau
FROM events e
JOIN users  u ON u.user_id = e.user_id
WHERE e.event_time >= CURRENT_DATE - INTERVAL '6 days'
GROUP BY u.country, DATE(e.event_time)
ORDER BY u.country, event_date;
```

**如果面试官要的是"7 日滚动去重活跃"（rolling 7-day uniques）**，必须先说破一个关键点：**日级 DISTINCT 数不能直接窗口求和**（同一用户跨天会被重复计数）。正确做法是对每个目标日 D 统计 [D−6, D] 内的去重用户：

```sql
WITH user_days AS (                      -- 先把 1 亿行事件压到 user-day 粒度
    SELECT DISTINCT u.country, e.user_id, DATE(e.event_time) AS d
    FROM events e JOIN users u ON u.user_id = e.user_id
),
days AS (SELECT DISTINCT d FROM user_days)
SELECT ud.country, dd.d AS as_of_date,
       COUNT(DISTINCT ud.user_id) AS rolling_7d_active_users
FROM days dd
JOIN user_days ud ON ud.d BETWEEN dd.d - 6 AND dd.d
GROUP BY ud.country, dd.d
ORDER BY ud.country, as_of_date;
```

**性能采分点（题面特意给了 1M users / 100M events）**: "First collapse events to the user-day grain (100M rows → a few million), partition-prune on `event_time`, and avoid running `COUNT(DISTINCT)` repeatedly over raw events. In production I'd materialize `user_days` as an incremental daily table — every DAU-family metric reads from it."

## D2. Upstream tables 还原题（电面 SQL 原题型：反推 take-home 数据的上游表并重建 final table）

**Answer schema（先画表，边画边讲）:**

```text
users                 (user_id, country, signup_date, plan_type)
experiment_assignments(user_id, experiment_id, variant, assigned_at)
exposures             (user_id, experiment_id, exposed_at)          -- assignment ≠ exposure，分开建表本身就是采分点

```

**重建 user-level 结果表（含 signup→cancel→再 signup 的 edge case【实锤考点】）:**

```sql
WITH exposed AS (
    SELECT a.user_id, a.variant, MIN(e.exposed_at) AS exposed_at
    FROM experiment_assignments a
    JOIN exposures e
      ON e.user_id = a.user_id AND e.experiment_id = a.experiment_id
    WHERE a.experiment_id = 'free_trial_2026'
    GROUP BY a.user_id, a.variant
),
-- 转化：曝光后的第一次 signup（重复 churn 用户只取第一次，避免重复计数）
first_signup AS (
    SELECT x.user_id, MIN(s.event_at) AS first_signup_at
    FROM exposed x
    JOIN subscription_events s
      ON s.user_id = x.user_id
     AND s.event_type = 'signup'
     AND s.event_at >= x.exposed_at
    GROUP BY x.user_id
),
-- 留存：D30 时点是否处于有效订阅 = 截至 exposed_at+30 的“最后一条”事件是 signup/reactivate 而非 cancel
status_d30 AS (
    SELECT user_id, event_type AS last_event_type
    FROM (
        SELECT s.user_id, s.event_type,
               ROW_NUMBER() OVER (PARTITION BY s.user_id ORDER BY s.event_at DESC) AS rn
        FROM subscription_events s
        JOIN exposed x ON x.user_id = s.user_id
        WHERE s.event_at <= x.exposed_at + INTERVAL '30 days'
    ) t
    WHERE rn = 1
)
SELECT x.user_id,
       x.variant,
       x.exposed_at,
       CASE WHEN f.user_id IS NOT NULL THEN 1 ELSE 0 END                    AS signed_up,
       f.first_signup_at,
       CASE WHEN d.last_event_type IN ('signup','reactivate') THEN 1 ELSE 0 END AS retained_d30
FROM exposed x
LEFT JOIN first_signup f ON f.user_id = x.user_id
LEFT JOIN status_d30  d ON d.user_id = x.user_id;
```

**口头要点**: (1) "conversion = *first* signup after exposure — repeat churners counted once"; (2) "retention is a point-in-time subscription-status check, not 'never cancelled'"; (3) "assignment vs exposure kept separate so we can analyze both ITT and treated, and run SRM on each"; (4) 主动和面试官确认口径再写——有面经因为想当然浪费了时间【实锤】。

## D3. Python 原题 ①：debug 分析代码（你贴的面经"问题 3"，代码已给出）

**Given:**

```python
def abtest(df):
    a = df[df['variant'] == 'A']['metric']
    b = df[df['variant'] == 'B']['metric']
    lift = (b.mean() - a.mean()) / a.mean()
    t, p = stats.ttest_ind(a, b)
    return lift, p
```

**Answer — the bugs & statistical traps（≥3 required；这里给 10 个，试题的 5 组 test case 每组都在打其中一个）:**

1. **No exposure filter.** Users with `exposure = 0` never saw the experiment; including them dilutes the effect (test case 2 has one). Decide the estimand explicitly: filter to exposed (treatment-on-treated) or keep all assigned (ITT) — but do it *consistently and on purpose*.
2. **NaN mishandling — and inconsistently.** `Series.mean()` silently skips NaN, but `stats.ttest_ind` with default `nan_policy='propagate'` returns `nan` p-values (test case 2 has a NaN). Worse, lift and the test end up computed on *different effective samples*. Decide semantics: for conversion-type metrics missing usually means 0 → `fillna(0)`; for usage-type metrics maybe exclude — state which and why.
3. **`equal_var=True` default (Student's t).** Treatments routinely change variance, not just means → use Welch: `ttest_ind(a, b, equal_var=False)`.
4. **No SRM check.** The constraints say the split may be unbalanced. Before reading any result, test observed counts against the intended ratio (chi-square/binomial); if SRM fires, the pipeline is broken — do *not* interpret the metrics.
5. **Division-by-zero / unstable relative lift.** `a.mean()` can be 0 (all-zeros arm) → crash or infinite lift; report absolute difference alongside relative lift, guard the denominator.
6. **Zero-variance crash.** Test case 4: every metric value = 1 → pooled variance 0 → t undefined (`nan`). Guard: if both arms constant, return "no detectable difference," not `nan`.
7. **Heavy tails / outliers.** Test case 3 has a 1000 among 0s: at small n the t-test is driven entirely by one point. Options: winsorize (changes estimand — say so), bootstrap the mean difference, or report rank-based checks as sensitivity. (When to use t vs proportion vs bootstrap vs nonparametric → 见 Q1.5，电面追问原题.)
8. **Binary metrics deserve a proportion test.** If `metric` ∈ {0,1}, report a two-proportion z-test with proper SE (asymptotically same as t, but it also fixes the zero-variance edge case cleanly).
9. **No input validation.** Variants other than A/B silently dropped; duplicate `user_id`s would violate the user-level-independence assumption — assert uniqueness (analysis unit must equal randomization unit).
10. **Output is decision-hostile.** A lone (lift, p) invites p < 0.05 worship: no CI, no absolute effect, no sample sizes. Return estimate + CI + n per arm; also note the sign convention — `lift` is B−A but `ttest_ind(a, b)` produces a t whose sign is A−B; harmless here but a classic review catch.

**Corrected code（写出来 or 口述均可）:**

```python
import numpy as np
import pandas as pd
from scipy import stats

def abtest(df, expected_split=0.5, fill_missing_as_zero=True):
    df = df.copy()
    assert df['user_id'].is_unique, "aggregate to one row per user first"
    df = df[df['variant'].isin(['A', 'B'])]
    df = df[df['exposure'] == 1]                      # analyze exposed (state ITT alternative)

    # --- SRM gate: never read results off a broken assignment ---
    n_a = int((df['variant'] == 'A').sum()); n_b = int((df['variant'] == 'B').sum())
    srm_p = stats.binomtest(n_a, n_a + n_b, expected_split).pvalue
    if srm_p < 1e-3:
        raise ValueError(f"SRM detected (p={srm_p:.2g}) — fix the pipeline before analysis")

    df['metric'] = df['metric'].fillna(0) if fill_missing_as_zero else df['metric']
    df = df.dropna(subset=['metric'])

    a = df.loc[df['variant'] == 'A', 'metric'].to_numpy(float)
    b = df.loc[df['variant'] == 'B', 'metric'].to_numpy(float)

    if len(a) < 2 or len(b) < 2:                      # 过滤后样本不足：var(ddof=1) 会变 nan（原题 test case 2 正打这个点）
        return {"n_a": len(a), "n_b": len(b), "note": "insufficient exposed sample per arm"}

    diff = b.mean() - a.mean()
    se = np.sqrt(a.var(ddof=1)/len(a) + b.var(ddof=1)/len(b))

    if se == 0:                                        # zero-variance guard (test case: all 1s)
        return {"diff": diff, "p": None, "note": "no variance in either arm"}

    if set(np.unique(np.concatenate([a, b]))) <= {0.0, 1.0}:     # binary → proportion z-test
        p_pool = np.concatenate([a, b]).mean()
        z = diff / np.sqrt(p_pool*(1-p_pool)*(1/len(a)+1/len(b)))
        pval = 2 * stats.norm.sf(abs(z))
    else:                                              # continuous → Welch
        _, pval = stats.ttest_ind(b, a, equal_var=False)

    return {
        "n_a": len(a), "n_b": len(b),
        "mean_a": a.mean(), "mean_b": b.mean(),
        "abs_diff": diff,
        "rel_lift": diff / a.mean() if a.mean() != 0 else np.nan,
        "ci95": (diff - 1.96*se, diff + 1.96*se),
        "p": pval, "srm_p": srm_p,
    }
```

（追问"偏态怎么办"→ 加 bootstrap 分支：resample 用户 5–10k 次取 mean difference 的分位数 CI。）

## D4. Python 原题 ②：debug 实验分组/触发代码（电面原题：assign users + trigger free trial，纯逻辑、无 syntax error，藏 7–8 个 bug【实锤】）

真实代码未公开，以下按多篇面经描述【推测还原】一段同类型代码——bug 类型与面经吻合，扫 bug 清单通用。

**Reconstructed buggy code:**

```python
import random

def run_experiment(users, current_subscribers, assignments):
    for user in users:
        if user.days_since_last_login > 30:        # (1)
            continue
        if random.random() < 0.5:                  # (2)
            group = 'treatment'
        else:
            group = 'control'
        assignments[user.id] = group               # (3)(4)
        if group == 'treatment':
            if user.id not in current_subscribers: # (5)
                send_free_trial_offer(user)        # (6)(7)
    return assignments
```

**The bugs（口头逐个指出，每个都说"后果 + 修法"）:**

1. **Selection at trigger time.** Only users active in the last 30 days enter — the sample is conditioned on run-date activity, and if this job runs repeatedly, entry timing differs by arm-uncorrelated luck. Consequence: results generalize only to active users; entry must be *logged* with timestamps. Fix: define eligibility once, log an entry event.
2. **Non-deterministic randomization.** `random.random()` re-rolls every invocation — rerun the job (or call it from two services) and the same user flips arms → crossover contamination. Fix: deterministic bucketing, e.g. `hash(f"{experiment_id}:{user_id}") % 1000 < 500`. (Also: seeding per-run doesn't fix it; determinism must be *per user*, not per run.)
3. **Silent re-assignment.** `assignments[user.id] = group` overwrites any existing assignment — combined with (2), users flip groups and treatment users can be re-offered. Fix: `if user.id in assignments: continue` (idempotency).
4. **No experiment scoping.** The key is bare `user.id` — a second concurrent experiment writing to the same store collides. Fix: key = (experiment_id, user_id).
5. **Eligibility checked on one arm only.** Subscribers are excluded from *receiving offers* in treatment, but remain in control's population → arms are drawn from different populations; any comparison of signup rates is biased (control contains people who *can't* convert — they already pay). Fix: filter `current_subscribers` (and any eligibility) **before** assignment, symmetrically.
6. **Exposure never logged.** We record assignment but not whether/when the offer actually reached the user (send can fail, user may never open the surface). Without an exposure log you cannot do treated analysis, cannot debug dilution — and without assignment logs on both arms **SRM is undetectable**. Fix: log `assignment(user, exp, variant, ts)` and `exposure(user, exp, ts)` events.
7. **Side effect before durable state.** The offer is sent before the assignment is persisted anywhere durable — a crash mid-loop yields users who *got* a free trial with no record of being in the experiment. Fix: persist assignment first, then trigger; make the trigger idempotent.
8. **No monitoring/guards at all.** No SRM alarm, no count logging, no cap on offers sent. Fix: emit counters per arm per day; alert on ratio deviation (chi-square p < 0.001).

**Fixed version（简版）:**

```python
import hashlib

def bucket(experiment_id, user_id, treatment_pct=50):
    h = hashlib.sha256(f"{experiment_id}:{user_id}".encode()).hexdigest()
    return 'treatment' if int(h, 16) % 100 < treatment_pct else 'control'

def run_experiment(users, current_subscribers, store, experiment_id="free_trial_2026"):
    for user in users:
        if user.id in current_subscribers:            # eligibility BEFORE assignment, both arms
            continue
        if store.get(experiment_id, user.id):         # idempotent: never re-assign
            continue
        group = bucket(experiment_id, user.id)        # deterministic per user
        store.log_assignment(experiment_id, user.id, group, now())   # persist FIRST
        if group == 'treatment':
            ok = send_free_trial_offer(user)          # idempotent send
            if ok:
                store.log_exposure(experiment_id, user.id, now())
    store.emit_srm_counters(experiment_id)            # monitoring hook
```

收尾金句【对应"亮点"要求】: "After launch, the first artifact I'd look at isn't the lift — it's the SRM dashboard. Every bug above except (7) shows up there."

## D5. Take-home 真题 ①：free trial A/B（地里原题）— 分析要点速答

Onsite 的 experiment case 很可能延续这个场景，把"坑位清单"带进考场（English, rapid-fire）:

- **SRM first**: verify assignment ratio before anything else.
- **Estimand**: ITT (all assigned) as primary — it's the decision-relevant number for "should we run this campaign"; treated/exposed as secondary.
- **Metric windows**: signup rate = first signup within K days of exposure; **conversion-to-paid = paid status after the trial ends** (a trial signup is not revenue); retention = point-in-time paid status at day 30/60/90 **after trial end**, cohort-aligned.
- **Censoring**: recent cohorts haven't matured — never mix maturities; report per-cohort curves.
- **Cannibalization（最大的坑）**: some treated signups would have subscribed anyway at full price — the control arm's organic signup rate estimates exactly this counterfactual; incremental signups = treatment − control, and the free month given to *non-incremental* subscribers is pure cost.
- **ROI**: incremental paid users × margin-LTV − [free-month cost (inference + forgone revenue) × all trial takers] ; there is no single "correct" LTV — present a sensitivity table over LTV/retention assumptions【实锤：面经原话 "ROI 没有所谓一定正确的算法，有道理都行"】.
- **Heterogeneity**: tenure, engagement level, platform, country — recommend *targeted* rollout (e.g., only segments with positive incremental ROI).
- **Novelty & seasonality**: was the test window representative (no launch spike/holiday)?
- **Stats**: two-proportion z-tests + CIs; multiple metrics → control the story, not 20 p-values.
